# 色彩层真实素材操作记录（2026-11-19）

本页记录用真实拍摄照片实际执行色彩链的结果。媒体、回执和驱动脚本都没有入仓，这里只给出来源、哈希和可复核的数值。结论只覆盖下文列出的素材、参数和环境：它属于**真实内容上的技术验证**，不是人工审美验收，也不是最终交付。

## 执行方式

- 每一步都通过 `python3 runtime/editing_runtime.py run --request … --work-dir …` 实际执行，调用的是 MCP `run_operation` 背后同一个 `runtime.run`。本环境的 MCP 服务没有配置 `EDITING_SKILL_WORK_ROOT`，`run_operation` 直接返回 `WORK_ROOT_REQUIRED`，所以改用命令行入口。
- 环境：Linux，Python 3.13.18，numpy 2.5.3，Pillow 12.3.0（LittleCMS 2.19），FFmpeg 6.1.1-3ubuntu5。
- 执行时的源码 SHA256 前 16 位：

  | 文件 | SHA256 前 16 位 |
  |---|---|
  | `color_grade_ops.py` | `d375bf34adea7e72` |
  | `color_ops.py` | `f4f25e88415404c7` |
  | `color_numerics.py` | `3efac503c1ea60aa` |
  | `color_profile_ops.py` | `90d55bb26e26f075` |
  | `still_ops.py` | `3bc1f925fa38b74f` |
  | `editing_runtime.py` | `1a98ceaaf2511d56` |

- 流程：
  1. 照片经 `still-image-render` 生成 420×280、24 fps、48 帧的缓慢推近视频；
  2. `color-profile-scan` 在 0.25、1.0、1.75 秒采样测量（分析尺寸 210×140）；
  3. `color-grade-compile` 以 65 阶编译风格；
  4. `color-lut-apply` 用四面体插值套用；
  5. 再用 `color-profile-scan` 复测；
  6. 抽 1.0 秒帧读回，与解析链的预测值逐像素比较。

## 被拒绝的输入（预期行为，也是衔接缺口）

| 步骤 | 输入 | 结果 |
|---|---|---|
| `still-image-render` | 原始 astronaut.png（内嵌 sRGB ICC） | `STILL_ICC_REQUIRES_NORMALIZATION` |
| `color-profile-scan`（verified-metadata 与 caller-declared 两种） | `still-image-render` 以 `input_color: srgb` 生成的视频，传输标签为 `iec61966-2-1` | `COLOR_PROFILE_METADATA_CONFLICT: color_transfer` |

**ICC 规范化**：本库没有做这一步的原子，因此在库外由调用方处理。
- 两张 sRGB 照片只剥离配置文件，并核对像素完全不变。
- rocket.jpg 用 LittleCMS 以相对色度意图从 Adobe RGB (1998) 转换到 sRGB。
- 规范化后的 PNG 不带 ICC、gAMA 或 EXIF，SHA256 前 16 位：astronaut `2418889d0d83962d`，coffee `1b334876bab6bccd`，chelsea `9540e8d656047041`，rocket `0f32a4704f2a7b39`。
- 如果直接把 Adobe RGB 码值当 sRGB 使用，颜色会系统性偏淡。这次的拒绝避免了这个错误。

**sRGB 照片进入色彩链**：后续步骤用 `input_color: bt709` 渲染，属于调用方声明：照片码值不做传输特性转换，按 BT.709 显示码值解释。像素路径与 `srgb` 声明完全相同，只有流标签不同。sRGB 与 BT.1886 γ2.4 在暗部的显示结果不同，这一差异属于声明的解释，而不是被测量出来的。

## 风格定义

| 风格 | 操作 | 65 阶编译自检（ΔE2000 中位 / p95 / 最大） | CLF |

## 管线精度：解析预测与实际输出

**比较方法**：
- **预测↔实测**：取源视频解码帧，用解析链计算预测值，再与 `color-lut-apply` 输出的解码帧逐像素比较（117,600 像素）。
- **重编码底**：同一源视频套用 65 阶恒等 LUT 后与源比较，衡量单纯 8 位 RGB 往返加 H.264 CRF 18 重编码的误差。
- **风格效果**：源与输出之间的中位 ΔE2000，用来衡量风格本身改变了多少。

| 镜头 | 风格 | 预测↔实测 中位 / p95 | 重编码底 中位 / p95 | 风格效果 中位 |
|---|---|---|---|---|
| astronaut | warm-teal | 0.95 / 2.98 | 0.69 / 2.53 | 3.67 |
| astronaut | warm-teal 0.6 | 0.94 / 2.81 | 0.69 / 2.53 | 2.36 |
| astronaut | clean-bright | 0.91 / 2.74 | 0.69 / 2.53 | 5.05 |
| coffee | warm-teal | 0.75 / 2.60 | 0.67 / 2.14 | 3.73 |
| coffee | warm-teal 0.6 | 0.75 / 2.41 | 0.67 / 2.14 | 2.51 |
| coffee | clean-bright | 0.75 / 2.31 | 0.67 / 2.14 | 5.96 |
| chelsea | warm-teal | 0.97 / 2.10 | 0.76 / 1.80 | 4.66 |
| chelsea | warm-teal 0.6 | 0.93 / 2.03 | 0.76 / 1.80 | 3.01 |
| chelsea | clean-bright | 0.91 / 1.95 | 0.76 / 1.80 | 6.15 |
| rocket | warm-teal | 0.70 / 3.57 | 0.43 / 3.54 | 3.24 |
| rocket | warm-teal 0.6 | 0.71 / 3.48 | 0.43 / 3.54 | 2.27 |
| rocket | clean-bright | 0.73 / 3.65 | 0.43 / 3.54 | 4.72 |

**有限结论**：
- 在这四张真实照片上，编译、FFmpeg `lut3d`、编码、解码整条链与解析模型的偏差，比重编码底高约 0.1–0.3 的中位 ΔE2000。
- 尾部误差（p95）主要来自重编码，包括 4:2:0 色度子采样和边缘处的有损压缩，不是 LUT 路径造成的。
- 风格效果的中位色差是这些偏差的 3–8 倍。
- 所有输出的流标签实测都是 bt709 / bt709 / bt709 / tv。

## 读回检查（代理目视，不是人工验收）

- 4 镜头 × 4 版本对比图：在 420×280 下，没有看到色相断裂、通道错位或明显色带。warm-teal 的肤色、咖啡油脂和猫毛明显更暖、更饱和，夜空偏向更深的蓝。
- 高光裁切图（任一通道 ≥254 标红）：clean-bright 在宇航员背景中航天飞机的白色机身上出现成片裁切，该局部为 5.5%（源 0.1%），机身细节丢失。
- 天空局部对比度放大 4 倍：三个版本都没有新增可见的色带，只有源压缩本身的块效应。

## 据此做的一次迭代

clean-bright 的裁切来自“曝光后硬钳位”，合同限制里已经写明它不是柔和的高光肩部。改用只带肩部的总曲线 `[[0,0.03],[0.35,0.42],[0.7,0.78],[0.9,0.94],[1,1]]` 加 CDL 饱和 1.08，再跑同样流程：

| 镜头 | 亮度 p50 源 / 原版 / 迭代 | 高光裁切 源 / 原版 / 迭代 |
|---|---|---|
| astronaut | 0.513 / 0.576 / 0.583 | 0.36% / 4.57% / 1.08% |
| coffee | 0.355 / 0.412 / 0.422 | 0.84% / 4.07% / 1.53% |
| chelsea | 0.461 / 0.523 / 0.538 | 0 / 0 / 0 |
| rocket | 0.203 / 0.251 / 0.258 | 0.12% / 0.31% / 0.18% |

中间调提亮幅度相同或略高。高光裁切比例相对原版：astronaut 降到约 24%，coffee 约 38%，rocket 约 58%，但都仍高于源。

## 发现与后续

1. **sRGB 静图无法如实进入色彩链**：`still-image-render` 以 `srgb` 声明时会写 `iec61966-2-1` 标签，色彩原子按合同拒绝。现在只能由调用方改为声明 `bt709`。是否让色彩原子接受 sRGB 传输（以及按哪条 EOTF 解释）是产品决定，本次没有改动。
2. **缺少 ICC 规范化原子**：四张真实照片里有三张带 ICC，其中一张不是 sRGB。现在只能拒绝，再由调用方在库外处理。建议列入 C4 的输入变换。
3. **提亮应优先用带肩部的曲线**：曝光和 CDL 都是硬钳位。提亮前后都应当用 `color-profile-scan` 对比高光裁切比例。
4. **肤色**：调整色相带中的橙色时，会同时移动人脸。涉及人物时，应声明面部区域，对比色相和肤色线偏移。
