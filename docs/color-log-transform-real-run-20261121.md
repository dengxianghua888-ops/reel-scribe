# 相机 Log 输入转换真实内容操作记录（2026-11-21）

本页第一部分记录 C4d `color-log-transform` 在真实照片内容上的一次运行；[第二部分](#第二部分真实拍摄场景数据编码的-log2026-11-22)改用真实电影拍摄的场景数据（有真实高光与噪声）编码成 Log 再转换。**Log 素材是合成的**：把真实照片做成的视频经 OpenColorIO 编码为 Apple Log 与 S-Log3，不是相机或手机拍摄的 Log 文件。所以这里能验证转换链（码值解释、矩阵、LUT 烘焙、编码、标签）是否把画面还原回来，不能验证真实相机文件的标签与范围。结论只覆盖下文的素材、参数和环境：属于真实内容上的技术验证，不是人工审美验收。

## 素材与执行

- **源**：与 [HDR 输入转换真实内容操作记录](color-input-transform-real-run-20261121.md)相同的未调色时间线，96 帧，420×280，24 fps，sRGB 标签，依次为宇航员、咖啡、猫、火箭四镜。
- **合成 Log**（4:2:0 10 位，libx264 CRF 10）：
  - 把 sRGB 码值经 sRGB 曲线转为线性光，当作 Rec.709 场景线性值，再用 OCIO 从 `Linear Rec.709 (sRGB)` 编码到相机 Log；
  - **Apple Log**：BT.2020 矩阵，全范围，带 `pc` 范围标签；
  - **S-Log3 S-Gamut3.Cine**：BT.709 矩阵，视频范围，带 `tv` 范围标签。
  - 照片的白是显示白，按场景线性 1.0 编码，所以素材里没有超过漫反射白的高光：Apple Log 码值的 0.1/99.9 分位为 0.140 / 0.697，S-Log3 为 0.089 / 0.600。
- **执行**：通过 `python3 runtime/editing_runtime.py run` 调用 5 次，全部成功，每次约 2 秒。配置为 `ocio://studio-config-v5.0.0_aces-v2.1_ocio-v2.6`，cube 65 阶，输出 `yuv420p10le`，采样第 12、36、60、84 帧。环境为 FFmpeg 6.1.1、Python 3.13、numpy 2.5、OpenColorIO 2.6.0；`log_ops.py` 的 SHA256 前 16 位为 `1741a4094d05255d`。
- **重跑说明**：CI 换到 FFmpeg 8.0 后，三条测试的结果与本地 FFmpeg 6.1 不同；为避开 swscale 在不同版本中的浮点与全范围转换差异，输出的 RGB → Y'CbCr 一步也改用 zscale。下表是改动后的重跑结果，与改动前相比各项变化都在 0.07 以内。

## 不做色调映射的往返

`Un-tone-mapped` 视图把场景线性值直接按显示编码。由于合成时把显示线性值当成了场景线性值，这一视图的输出应当回到原画面。

| 运行 | 与原画面的逐片段中位 ΔE2000（宇航员 / 咖啡 / 猫 / 火箭） | 读回中位 / p95 | 超出显示范围被裁剪 |
|---|---|---|---|
| Apple Log → Rec.1886 显示 | 0.78 / 0.67 / 0.73 / 0.47 | 0.67 / 2.61 | 2.98% |
| Apple Log → sRGB 显示 | 0.77 / 0.63 / 0.71 / 0.47 | 0.64 / 2.52 | 2.95% |
| S-Log3（视频范围、BT.709 矩阵）→ Rec.1886 显示 | 0.89 / 0.71 / 0.85 / 0.50 | 0.73 / 2.64 | 2.69% |

- 三条链路都把画面还原到原画面附近，中位误差与此前 SDR 色彩链路的读回误差在同一量级。读回 p95 约 2.6，主要来自 4:2:0 色度在颜色边缘的误差。
- 被裁剪的约 3% 主要是原本就接近白色的像素：经 10 位编码和 4:2:0 之后略超出 1。回执对这一项给出了提示。

## ACES 2.0 SDR 视图

同一段 Apple Log 改用 `ACES 2.0 - SDR 100 nits (Rec.709)` 视图：

| 片段 | 原画面 L* 中位 / p99 | ACES 2.0 SDR 输出 L* 中位 / p99 |
|---|---|---|
| 宇航员 | 57.1 / 96.9 | 45.0 / 71.7 |
| 咖啡 | 44.8 / 94.8 | 33.2 / 70.8 |
| 猫 | 50.9 / 72.6 | 39.2 / 57.4 |
| 火箭 | 22.4 / 77.3 | 8.5 / 60.5 |

- 整体暗了约 12–14 个 L*，最亮处从接近 97 降到约 72。ACES 的输出变换把场景线性 1.0（这里是照片的白）放在显示白之下，给更亮的高光留出空间；本素材没有高光，所以只表现为整体变暗。
- 这说明视图的选择决定画面：同一段 Log，选不同视图得到的结果差别很大，代码不替上层选。
- 这一视图没有像素超出显示范围（ACES 的色调曲线把高光压进范围内），读回中位 ΔE2000 为 0.57。

## LUT 烘焙误差

| 视图 | 烘焙误差中位 / p95 / 最大（ΔE2000） | 网格点超出显示范围的比例 |
|---|---|---|
| ACES 2.0 SDR | 0.011 / 0.12 / 0.64 | 0% |
| Un-tone-mapped（Apple Log） | 0.005 / 0.22 / 4.7 | 94.8% |
| Un-tone-mapped（S-Log3） | 0.000 / 0.44 / 14.7 | 97.7% |

不做色调映射时，Log 码值的大部分范围对应远超显示白的场景亮度，网格点几乎都被裁剪。误差最大值出现在裁剪边界附近：精确结果在边界处有折角，插值把它抹平了。中位数和 p95 都很小，读回也通过了。

## 码值范围声明错误

把全范围的 Apple Log 文件声明为 `video` 码值：

- 运行照常成功，读回也通过：读回比较的是“按声明解码后的预测”与输出，声明本身错了，读回看不出来。
- 与原画面的逐片段中位 ΔE2000 升到 2.3–3.9，L* 的 p99 普遍升高（宇航员 96.9 → 99.7），被裁剪的像素从 3% 升到 28%。
- 回执给出了两条提示：文件的范围标签是 `pc`，与声明不符；28% 的像素超出显示范围。
- 码值超出 [0,1] 这一项没有触发：本素材没有超过漫反射白的高光，最亮的码值约 0.70，按视频范围展开后仍在 1 以内。这项测量只对高光多的素材有用；范围是否声明对，主要靠上层核对拍摄设置，以及看文件的范围标签提示。

## 不能据此声称

- 没有用真实相机拍摄的 Log 文件验证；真实文件的范围标签、矩阵标签与曲线定义之间的关系需要上层按厂商资料核对。
- 合成时把显示线性值当作场景线性值，素材没有真正的高光，不能代表真实 Log 素材的动态范围。
- 不代表任何视图“效果更好”；ACES 2.0 SDR 的整体变暗是这类素材（照片白放在场景 1.0）的结果，换成曝光正常的真实 Log 素材，结论会不同。
- 只采样 4 帧；素材是静态照片推近的视频。

## 第二部分：真实拍摄场景数据编码的 Log（2026-11-22）

第一部分的素材没有高光，也没有传感器噪声。这一部分改用真实电影拍摄的场景数据：Netflix Open Content 短片《Sparks》的 ACES 图像序列（CC BY 4.0，许可文本与图像取自 `https://s3.amazonaws.com/download.opencontent.netflix.com/sparks/` 下的 `aces_image_sequence_59_94_fps/` 与许可文件；素材未入仓）。这些帧是摄影机原始素材转换成的 ACES2065-1 场景线性值，带有真实的焊花高光和噪声。

**Log 文件仍是本库做的**：把场景值经 OCIO 编码成 Log，再由 FFmpeg 写成文件，不是相机写出的文件。能验证的是转换链在真实动态范围和噪声上的表现，以及声明错误时回执能否发现；相机文件的实际标签、范围与矩阵仍未验证，需要用户提供真实相机素材。

### 素材与执行

- **帧**：序列中的 8 帧（01000、02700、04400、06100、07800、09500、11200、12900，最后一帧是深色背景的字幕卡），4096×2160 半浮点 EXR。FFmpeg 的 EXR 解码器直接输出 `gbrpf32le`，没有格式转换；在线性光中 2×2 平均为 2048×1080。每帧保持 6 帧，共 48 帧，24 fps；采样每段中间一帧。
- **场景**：前 7 帧的 ACES 亮度中位数 0.07–1.35，p99 1.1–30，最大值 8.3–781（焊花、天空）。
- **编码**：OCIO 从 `ACES2065-1` 编码到 Log；超出 [0,1] 的码值裁剪，相当于记录时的饱和（Apple Log 有 1.07% 的像素至少一个分量超出，S-Log3 为 0.16%）；zscale 转 Y'CbCr。
  - **Apple Log**：BT.2020 矩阵，全范围，libx265 Main10 4:2:0，CRF 12，标签 `pc`、`bt2020nc`。
  - **S-Log3 S-Gamut3.Cine**：BT.709 矩阵，视频范围，ProRes 422 HQ（prores_ks）4:2:2。本次 FFmpeg 6.1.1 写出的 ProRes 文件，ffprobe 读不到任何色彩标签。
- **执行**：用 `runtime/editing_runtime.py run` 调用 5 次，全部成功，每次 7–9 秒（4 核，同时在跑测试）。配置 `ocio://studio-config-v5.0.0_aces-v2.1_ocio-v2.6`，cube 65 阶，输出 `yuv420p10le`。环境为 FFmpeg 6.1.1、Python 3.13、numpy 2.5、OpenColorIO 2.6.0；`log_ops.py` 的 SHA256 前 16 位为 `b6db11bdd8709a2a`。
- **对照**：OCIO 直接把场景值按同一显示和视图转换，不经过 Log、编码和 cube，作为“场景真值”；另把记录时裁剪后的精确 Log 码值经 OCIO 转换，作为“记录真值”。输出按 BT.709 有限范围用 zscale 解码，与真值比较 ΔE2000（每 4 个像素取 1 个）。

### 结果

| 运行 | 与场景真值的逐镜头中位 ΔE2000（7 个画面镜头） | 逐镜头 p95 | 读回中位 / p95 | 回执测量与提示 |
|---|---|---|---|---|
| Apple Log（HEVC）→ ACES 2.0 SDR | 0.71–1.99 | 3.4–7.6 | 0.52 / 2.57 | 码值超出 [0,1] 0.14%，99.9 分位码值 1.0006；无提示 |
| S-Log3（ProRes）→ ACES 2.0 SDR | 0.68–2.01 | 3.4–7.5 | 0.65 / 3.17 | 码值超出 0.02%；无提示 |
| Apple Log → Un-tone-mapped | 0.99–2.72 | 4.0–9.3 | 0.64 / 3.05 | 23.2% 的像素超出显示范围，给出提示 |

字幕卡一帧的误差都在 0.05 以内。

- **与记录真值几乎相同**：每个镜头与场景真值、与记录真值的结果相差不超过 0.06。记录时被裁剪的高光和相机色域外的颜色，在这两个视图下对这些帧没有可见影响。
- **误差来源**：两个视图的误差都在细节和噪声上。以 ACES 2.0 SDR 为例：
  - 只看 Log 文件本身：解码后的码值与精确码值相差中位 1.5–3.1 个 10 位码值（Apple Log HEVC）、1.0–2.4（S-Log3 ProRes），p95 到 6–18；用解码后的码值预测的画面与真值相差中位 0.45–1.66。
  - 从解码后的 Log 到输出（cube、4:2:0 编码）：中位 0.39–1.19。
  - 两个图像都做 8×8 平均后再比较：中位 0.22–0.61，p95 0.93–1.93。
  - a*、b* 的平均偏差都在 ±0.3 以内，没有整体偏色。
  - 也就是说，逐像素的误差主要来自 Log 记录和输出编码对噪声细节的损失，转换本身没有系统偏差。真实相机文件的压缩方式不同，这一部分会不同。
- **烘焙误差**（中位 / p95 / 最大）：Apple Log ACES SDR 0.011 / 0.115 / 0.64，S-Log3 0.015 / 0.156 / 1.42，Apple Log 不做色调映射 0.005 / 0.22 / 4.72。
- **视图**：ACES 2.0 SDR 把亮度高达几百的焊花和天空压进显示范围，没有像素被裁剪；不做色调映射时天空大片裁白，回执的提示与画面一致。

### 码值范围声明错误

| 情况 | 回执 | 与场景真值的逐镜头中位 ΔE2000 |
|---|---|---|
| 全范围 Apple Log 声明为 `video` | 成功；两条提示：范围标签为 `pc` 与声明不符；6.01% 的码值超出 [0,1] | 2.17–3.91 |
| 视频范围 S-Log3 声明为 `full` | 成功，**没有任何提示** | 2.52–3.12，字幕卡黑底被抬高（0.26） |

- 有真实高光时，“码值超出 [0,1]”这一项能发现把全范围当成视频范围的错误；第一部分没有高光，这一项没有触发。
- 反方向的错误发现不了：视频范围的码值按全范围解释，全部落在 [0,1] 内，不会超出；文件又没有范围标签，也没有标签冲突可提示。读回比较的是按声明的预测，同样通过。画面整体发灰、黑位抬高。代码不加启发式判断：许多正确的全范围 Log 素材，码值同样落在 64–940 之间。这种情况只能靠上层按拍摄设置和厂商资料确认范围。

### 不能据此声称

- 不是相机写出的 Log 文件：编码、封装和标签是本库选的。真实相机文件的范围标签、矩阵标签与曲线定义之间的关系仍未验证。
- 场景数据经过了 Netflix 的处理链（原始素材转换为 ACES），本库没有核对那一步。
- 只用 8 帧静止画面，每帧保持 6 帧，没有运动；只试了 Apple Log 与 S-Log3 两种曲线、两个视图。
- 不代表任何视图“效果更好”，也不是人工审美验收。
