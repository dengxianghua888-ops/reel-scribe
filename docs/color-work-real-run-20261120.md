# 作品调色真实素材操作记录（2026-11-20）

本页记录作品调色在真实照片素材上的三次完整运行：第一部分是 C2a（调色段与渲染），第二部分是 C2b（A/B 预览、配方、影响分析和局部撤销），第三部分是 C2c（保护项与调色门禁）。媒体与回执没有入仓，这里给出来源、哈希和可复核的数值。结论只覆盖下文的素材、参数和环境：它属于**真实内容上的技术验证**，不是人工审美验收，也不是最终交付。

# 第一部分：C2a 调色段与渲染

- **作品**：4 个片段，每段 1 秒、24 fps，共 96 帧，顺序为宇航员、咖啡、猫、火箭。第一个片段上有一条白色字幕（DejaVu Sans 28 号，`FFFFFF`）。

## 第一次运行暴露的问题与修正

第一次 `work-render` 在调色步骤失败，报 `COLOR_METADATA_CONFLICT: color_transfer`：
- 时间线渲染会把第一个片段素材帧上的标签带进输出，这里是 `bt709 / iec61966-2-1 / bt709`；
- 而调色步骤按 BT.709 声明。

修正方式：调色步骤沿用时间线输出的实际传递函数标签。标签为 sRGB 时按 `srgb-sdr` 套用并保持该标签；为 BT.709 或缺失时按 `bt709-sdr`；其他标签直接拒绝。LUT 只作用于码值，每个调色层的解释已经在作品校验阶段按素材逐一核对，因此标签只用于一致性检查和保持管线原有的标签。这个情况已补上回归测试。

## 第二次运行结果

**子操作顺序**：时间线 → `color-grade-compile` ×2 → `color-lut-apply`（layers）→ `caption-burn` → `media-qc`，全部成功。

**分层区间**：`rocket-correction` 只作用于第 72–95 帧，`look` 作用于全部 96 帧。

**内置读回**（`color-lut-apply` 自检，逐点取样）：第 47 帧（`look`）和第 83 帧（两层叠加）与预测的 ΔE2000 中位数分别为 0.770、0.700。

> 本部分的数值来自 PR #28 两轮评审修复后的重跑。修复前读回先做面积平均再预测，两帧分别为 0.683、0.673；改为逐点取样后不再平均编码噪声，数值略高。修复只影响读回检查：渲染输出的视频字节与修复前相同（SHA256 前 16 位 `d7c5364ca6844bde`），逐片段核对结果也不变。

**逐片段核对**：取每个片段的中间帧，比较渲染输出与“解析链作用于时间线帧”的预测值，单位为 ΔE2000，按 sRGB 解释计算：

| 片段 | 帧 | 预测↔输出 中位 / p95 | 调色效果 中位 |
|---|---|---|---|
| 宇航员（不含字幕区域） | 12 | 0.90 / 2.69 | 3.66 |
| 咖啡 | 36 | 0.74 / 2.48 | 3.80 |
| 猫 | 60 | 1.01 / 2.31 | 4.57 |
| 火箭（两层叠加） | 84 | 0.65 / 3.13 | 3.52 |

偏差量级与前两轮单段视频的结果一致：中位约 0.7–1.0，主要来自重编码。

**字幕没有被调色**：字幕区亮度最高 0.5% 的像素均值为 (255, 255, 255)。若白色经过 `look`，会变成 (255, 254.7, 251.1)。两者只差约 4 个码值，信号较弱；更强的依据是渲染顺序：字幕在调色之后合成。

**读回目视**（代理检查，不是人工验收）：
- 调色后整体更暖、对比更强；
- 火箭一镜因校正层更亮，高光没有成片裁切；
- 字幕边缘清晰，没有色带或色相断裂。

## 顺带发现并修正的问题

为 C2a 写的合成素材测试发现，`visual-layer-render` 会让彩色叠层偏色：(30, 180, 40) 变成 (14, 155, 32)。灰色叠层不受影响，所以旧测试没有暴露。

原因是用 `colorchannelmixer` 调不透明度。它只接受 RGB，FFmpeg 会自动插入 YUV→RGB→YUV 转换，而两次转换使用的矩阵不一致（BT.709 与默认的 BT.601）。

现在叠层全程保持 YUVA：缩放时显式指定 BT.709 矩阵与有限范围，不透明度改用 `lut=a=val*opacity` 直接缩放 alpha 平面。回归测试覆盖不透明度 1 和 0.5 两种情况，旧滤镜链会让测试失败。这个问题与作品调色无关，没有调色段的作品同样受影响。

## 不能据此声称

- 不代表任何调色好看，也不代表适合某个平台；风格参数是沿用前两轮的测试值。
- 素材仍是静态照片做的推近视频，没有覆盖摄影机原生视频、多机位混合素材、Log、HDR 或 10 位源。
- 传递函数混用的时间线（例如 sRGB 照片和 BT.709 视频混剪）只在测试里按声明逐片段校验，没有用真实素材实测。
- 局部撤销、风格配方参数组和 A/B 预览见第二部分；保护项门禁见第三部分。

# 第二部分：C2b A/B 预览、配方、影响分析与局部撤销

## 素材与执行

- **素材**：与第一部分相同的 4 段视频，420×280、24 fps，每段 1 秒，共 96 帧。本轮没有字幕和叠层。
- **初始作品**：`color` 段只声明 `inputs`（4 个素材都是 `srgb-sdr`、`verified-metadata`），没有调色层。
- **两个调色配方**，都用 `srgb-sdr-display` 解释、65 阶 LUT、作用于全部片段，调色层 ID 都是 `look`：
  - `warm-teal`：与第一部分的 `look` 相同（白平衡、S 曲线、HSL）。
  - `clean-bright`：曝光 +0.25 档 → `highlight_rolloff`（knee 0.8，headroom 0.5 档）→ 抬黑曲线 → CDL 饱和度 1.08。
- **操作序列**，全部通过 `python3 runtime/editing_runtime.py run` 调用：
  1. `style-recipe-preview`：两个配方各自编译成候选并渲染，不提交；
  2. 采纳 `warm-teal`：`style-recipe-compile` 后 `commit`（版本 2）；
  3. 配方升级到 `warm-v2`：橙色饱和度 1.1 → 1.3。先 `revision-impact-inspect`，再 `commit`（版本 3）；
  4. 撤销版本 3 对 `ops` 的修改：`prepare-local-undo`，选择器为 `{kind: color_grade, id: look, field: ops}`，附显式 `binding_resolution`，派生配方版本为 `warm-v2-undo-ops`，然后 `commit`（版本 4）；
  5. `work-render` 渲染版本 4。
- **执行时的源码 SHA256 前 16 位**：两部分在同一份代码上运行，第一部分表中的文件哈希相同，这里只列本部分新涉及的文件。

## 结果

11 次运行时调用全部成功。

**A/B 预览不改作品**：预览后重新读取作品，版本令牌与预览前相同。预览结果自身也标明 `applied_to_work: false`、`style_effect: NOT_VERIFIED`、`adoption_authorized_by_preview: false`。

**影响分析**（版本 2 → 配方 v2 的候选）：

- 分类：`color-grade-or-order`、`style-metadata`；
- 需重做阶段：只有 `color-grade` 和 `render`；
- 未变依赖阶段：素材分析、内容计划、时间线、字幕排版、混音、视觉合成；
- 失效复核：内容复核、听检、渲染、技术 QC、画面复核。这沿用现有的整份文档失效规则，没有因为“只改了调色”而放宽。

**局部撤销**：

- 作品的配方绑定改为 `warm-v2-undo-ops`；派生配方中橙色带恢复为饱和度 1.1、色相 +3，其余与 v2 相同。

**逐片段核对**：取每个片段的中间帧，比较输出与“解析链作用于时间线帧”的预测值，单位为 ΔE2000（按 sRGB 解释），表中是中位数：

# 第三部分：C2c 保护项与调色门禁

## 素材与执行

- **素材**：与前两部分相同的 4 段视频，共 96 帧，没有字幕和叠层。
- **调色**：调色层 `look` 作用于全部片段：白平衡增益 (1.08, 1.0, 0.9)、S 曲线、HSL（橙色饱和度 1.25、色相 +6，另调绿、青、蓝）。比前两部分的 warm-teal 更暖，用来制造需要拦截的情况。
- **保护项**：
  - `skin`：只针对宇航员一镜，CIELAB 色相 20°–70°、色度 ≥ 12，限定在脸部框 `[0.33, 0.02, 0.52, 0.28]` 内，中位 ΔE2000 上限 2.0，动作 `fail`。框是看了这一镜第 0 帧和第 23 帧后人工声明的，推近过程中脸都在框内。
  - `saucer`：只针对咖啡一镜，碟子所在的区域 `[0.2, 0.62, 0.8, 0.95]`，上限 2.0，动作 `flag`。
- **上限**：`max_clip_increase` 0.03。
- **操作序列**，全部通过 `python3 runtime/editing_runtime.py run` 调用：`work-version` init → `work-render`（v1）→ `timeline-revise`（范围 `grade_ids: [look, look-soft]`）→ `work-version` commit → `work-render`（v2）。v2 把 `look` 的目标改为另外三镜，宇航员一镜换成同样参数、降低强度的 `look-soft`。

  | 文件 | SHA256 前 16 位 |
  |---|---|
  | `color_check_ops.py` | `5e02742ced4ca26c` |
  | `work_color.py` | `24047a3daf4b05bb` |
  | `work_ops.py` | `eb08acaf5cc9cf61` |
  | `revision_impact.py` | `b43ef4d21ddcdd40` |
  | `color_ops.py` | `f6d6db1151e8fc9c` |

## 第一次尝试暴露的问题

最初的肤色保护项没有限定区域，只按色相和色度选像素。宇航员一镜选中了 42985 个像素，其中九成以上落在脸部框外，主要是橙色宇航服。这样测的是“橙色东西变了多少”，不是皮肤。

为此给 `hue-range` 增加了可选 `box`：色相选择只在调用者声明的矩形内进行。加框后选中 3896 个像素，下面的结果都用加框的保护项。

## 结果

**v1：完整 look 被门禁拦下**。渲染以 `WORK_COLOR_CHECK_FAILED: protection skin violated` 中止，后续的 QC 等步骤没有执行。

| 保护项 | 选中像素 | 中位 / p95 ΔE2000 | 状态 |
|---|---|---|---|
| `skin`（脸部） | 3896 | 7.83 / 9.18 | VIOLATED（fail） |
| `saucer`（碟子） | 26334 | 2.97 / 5.59 | VIOLATED（flag） |

**降低强度，直到通过**。按门禁读数逐步降低宇航员一镜的强度，每次都是一次完整的 init → render → revise → commit → render：

| `look-soft` 强度 | 脸部中位 / p95 ΔE2000 | 门禁 |
|---|---|---|
| 0.35 | 3.24 / 4.54 | FAILED |
| 0.20 | 2.04 / 3.41 | FAILED |
| 0.15 | 1.55 / 2.83 | 通过（skin KEPT） |

强度 0.15 的 v2 渲染成功，门禁为 `FLAGGED`：`saucer` 仍为 VIOLATED（2.96），但它的动作是 `flag`，只记录、不阻断。

**门禁读数可信**：对宇航员一镜的三个样本帧，在全分辨率上用 numpy 独立重算框内肤色像素的中位 ΔE2000。v1 为 7.94（门禁 7.83），强度 0.2 时为 2.09（门禁 2.04），0.15 时为 1.545（门禁 1.55）。门禁按 256 宽逐点取样，与全分辨率结果相差不到 0.12。

**剪切**：v1 宇航员一镜高光剪切增加 2.36 个百分点，在上限 3% 以内；v2 降到 -0.02 个百分点。

**相邻镜头漂移出现取舍**：宇航员与咖啡两镜平均颜色的 ΔE2000，调色前为 11.96，v1 为 11.93，v2 为 14.62。保护了脸部肤色，这一镜就没有跟上其他镜头的暖调，两镜的差距反而变大。门禁只报告这个数，没有声明漂移上限时不阻断；是否接受由人决定。

**读回目视**（代理检查，不是人工验收）：宇航员一镜并排看，完整 look 的脸明显偏橙、偏红，强度 0.15 的版本与调色前接近。

## 第三部分不能据此声称

- 保护项只保证脸部框内、符合色相条件的像素变化不超过阈值，不判断原来的肤色是否“正确”，也不代表这一镜看起来自然。
- 脸部框是人工看帧后声明的，不是检测结果；人物移动较大的镜头，固定框会框不准。
- 只测了每镜 3 个样本帧。
- 强度是按门禁读数手动逐步调整的，不是自动求解；更好的做法（例如只在这一镜去掉橙色带的调整）没有尝试。
- 素材与环境同前两部分，前两部分的覆盖范围限制同样适用。
