# 04 Harness 落地：同一套能力，四种运行方式

Harness 指把模型接到工具、状态和权限上的宿主程序。同一套影述能力会在四种 harness 里运行，它们的上下文策略、工具面、并行方式和状态权威各不相同。本章逐一给出规格，再列出跨 harness 必须一致的部分。

| 编号 | 运行方式 | 对应阶段 | 状态权威 |
| --- | --- | --- | --- |
| H1 | 通用编码 Agent（Claude Code、Codex 等）加载影述插件与本地 MCP | A 离线验证（现状） | 本地 Work（SQLite） |
| H2 | 外部 Agent 通过 MCP 操作自研剪辑 Agent 桌面 | B 外部接入 | 剪辑 Agent 工程 |
| H3 | 剪辑 Agent 内置 Agent | C 应用内置 | 剪辑 Agent 工程 |
| H4 | 无界面评测批跑 | 贯穿各阶段 | 每次试验独立的临时工程 |

## 一、H1：通用编码 Agent + 影述插件

这是今天用户实际使用影述的方式。

| 项 | 现状 | v2 规格 |
| --- | --- | --- |
| 入口 | 插件只暴露一个入口 Skill，要求先读完注册表与 `router.md` | 入口 Skill 只含硬规则与工具组说明（1,500–3,000 token）；场景卡与方法卡作为独立 Skill 或参考文件按需读取 |
| 技能列表 | 1 个 | 活跃场景卡各一个 Skill（阶段 1 为 2 个），描述写清“何时用、何时不用”；休眠场景不注册为 Skill，只作参考文件 |
| 工具面 | 3 个 MCP 工具，`run_operation` 接约 50 种操作 | 约 10 组命名空间工具，每组附 `describe`；工具定义多时用宿主的工具检索 |
| 并行 | 无 | 取证用子代理：工具白名单只含 `media.*`、`transcript.*`、`evidence.*`、`work.read`，交回 `evidence-record/1`；批量取证可用宿主的动态工作流 |
| 写入 | 模型拼完整 JSON | 只经 `edit.propose` / `edit.commit`，哈希与版本由运行时持有 |
| 花钱的调用 | 合同要求另行授权 | `gen.submit` 每批都需要用户确认或在任务单预算内；`gen.preflight` 不过不发单 |
| 遥测 | 回执分散在各工作目录 | 每个任务汇总 `cost`：token、调用数、时长、积分、人工介入 |

**为什么技能列表要短。** 宿主通常只把每个 Skill 的名称和描述放进上下文，并给技能列表设预算；超出预算的描述会被截断，有项目报告大批技能因此“隐身”（第三方报告，待核）。活跃 Skill 少而准，比把所有能力都注册成 Skill 更可靠。

**子代理的边界。** 子代理在自己的上下文里工作，适合“从一百段原片里找出有这个人的片段”。它不能写工程：被重启的代理已经改过的文件会保留（Claude Code 工作流文档写明了这一点），多个写者还会互相覆盖。动态工作流适合批量取证与批量检查，不适合需要用户中途确认的步骤。

**Codex 等其他宿主。** 能力相同时按同一规格实现：Skill 目录放场景卡，MCP 提供工具组，子代理按只读白名单配置。宿主不支持子代理时，取证改为主 Agent 顺序调用读取组，证据记录格式不变。

## 二、H2：外部 Agent 操作剪辑 Agent 桌面

阶段 B 的目标是让外部 Agent 在用户的剪辑 Agent 工程里完成预演、采用和撤回。研究库任务卡已经定义了 I0–I7，剪辑 Agent 现有 5 个只读 MCP 工具（`list_projects`、`list_works`、`get_timeline_summary`、`list_candidates`、`list_skills`）。

| 项 | 规格 |
| --- | --- |
| 状态权威 | **剪辑 Agent 工程是唯一权威**。影述 SQLite Work 不参与；影述的合同语义由宿主实现 |
| 编译在哪里 | 影述作为库或 MCP 服务提供编译与检查：读取宿主工程（I0、I2）→ 接收 `edit-intent/1` → 编译成宿主编辑会话的修改组（I1、I4、I5）→ 宿主预演 → 采用 → 读回 |
| 工具面 | 与 H1 相同的工具组名称；`work.*` 与 `edit.*` 的后端换成宿主 I0/I1 |
| 写入安全 | 宿主编辑会话必须支持：基准修订校验、操作号幂等、预演不落盘、手改对象拒绝旧候选、撤回保留无关手改（研究库任务卡 I1 的边界用例） |
| 一致性测试 | 把影述现有约 1,500 个测试中与合同语义相关的部分（版本冲突、范围候选、保护项、三方撤销、未知态读回）改写成**宿主一致性测试套件**，在剪辑 Agent 上运行 |
| 风格与组件 | 组件优先用宿主原生实例（I5），效果不够时放渲染件（I9）；多风格变体经 I10 |
| 退出条件 | 同一工程内多风格预演、采用、撤回、冷开、导出，读回全部一致；一致性测试全部通过 |

两套权威状态是阶段 B 最大的风险：如果外部 Agent 同时维护影述 Work 和宿主工程，两边迟早不一致。v2 的立场是迁移合同，不迁移 SQLite。

### 兼容模式与接入模式（已定）

影述 Skill 保持兼容，可以脱离剪辑 Agent 独立运行；一旦接入，剪辑 Agent 工程就是唯一权威。

| 模式 | 何时进入 | 作品状态在哪 | 写入走向 | 本地 Work |
| --- | --- | --- | --- | --- |
| 兼容模式 | 没有配置剪辑 Agent 连接，或连接不可用 | 影述本地 Work（SQLite） | 编译结果提交到本地 Work | 正常读写 |
| 接入模式 | 剪辑 Agent 连接可用，且任务指向剪辑 Agent 中的项目 | 剪辑 Agent 工程 | 编译结果提交到宿主编辑会话（I1） | 只读，不新建作品 |

- **判定写进任务单。** 主 Agent 在任务单的 `state_authority` 字段写明 `local-work` 或 `host:<项目 ID>`。任务进行中不切换；连接中断时停止写入并报告，不自动退回本地 Work。
- **一次性导入，不双向同步。** 本地作品可以导入宿主工程，包括片段、音轨、字幕、保护项和风格绑定。导入成功并读回一致后，本地作品标为 `migrated`，此后只在宿主修改。
- **同一作品不在两边同时存在可写副本。** 发现同一素材集在两边都有可写作品时，以宿主为准，本地副本标为只读并提示用户。

## 三、H3：剪辑 Agent 内置 Agent

| 项 | 规格 |
| --- | --- |
| 场景选择 | 用户点场景卡即为“指定组”，不做语义路由；自由输入时才走任务单解析（检索 + 门控） |
| 工具面 | 宿主原生实现的工具组；名称与参数与 H1/H2 一致，便于用 H4 复测 |
| 角色 | 主 Agent（唯一写者）；取证助手（只读，可并行）；评审者（独立上下文，只看成片与任务单） |
| 界面绑定 | 任务单可见可改；方向对照面板读 `style-route-result/1`；属性面板写 `set_component_props`；版本面板读回执 |
| 记录 | 偏好事件（盲选、方向选择、采用、撤回、手改）按已定的知情同意规则记录 |
| 退出条件 | 首页卡片、方向对照、属性面板可用；“只改第二处”局部修改例在冷开与导出后通过 |

研究库对 ChatCut 的拆解显示，它把两百多个工作流放在界面上，以卡片加表单让用户先定好素材角色。这在产品上等于把路由做成了“指定组”，模型自选带来的损失在入口处就消掉了。H3 应该充分利用这一点。

## 四、H4：评测批跑

| 项 | 规格 |
| --- | --- |
| 隔离 | 每次试验从同一份冻结初态复制出独立工程与工作目录；不共享缓存与历史 |
| 固定 | 模型版本、推理强度、工具组版本、场景卡版本、素材清单与哈希全部写入试验记录 |
| 重复 | 每个任务至少 3 次独立运行，算 pass@3 与 pass^3 |
| 记录 | 每次运行的 token、调用数、时长、积分、失败位置、读回结果、证据记录 |
| 组别 | 支持 Oracle（指定技能）、Auto（自选）、None（不给）三组，以及接口阶梯与分工阶梯（见 [05](05-metrics-experiments.md)） |
| 节奏 | 每次合并到 main 跑回归子集；每次模型升级跑全量；每个阶段放行前跑对应实验 |

H4 用的工具组与 H1 相同，所以 H1 的改动可以直接在 H4 中量化。

## 五、模型角色

| 角色 | 需要的能力 | 建议 |
| --- | --- | --- |
| 主 Agent | 长上下文判断、工具调用、听懂中文委托 | 用最强的可用模型；推理强度按任务类型设，并记录成本 |
| 取证助手 | 多模态读取（帧、音频、转写），按格式交回 | 可用更快更便宜的模型；必须记录 `method`（抽帧间隔、是否听音频） |
| 评审者 | 独立判断可核对的问题 | 与主 Agent 不共享上下文；先在带人工标签的片段上测一致率；A/B 题左右各问一次 |
| 编译器与检查器 | 确定性 | 不用模型 |

评审模型的默认输入可能很粗：例如 Gemini API 文档写明视频默认每秒 1 帧抽样、音频 1 Kbps 单声道。剪点、闪帧、口型、响度一律交给程序检查；需要模型看剪点时，只送剪点前后的高帧率片段。

## 六、跨 harness 必须一致的部分

| 项 | 要求 |
| --- | --- |
| 工具组名称与参数 | 四种 harness 相同，差别只在后端 |
| 数据契约 | `task-spec/1`、`evidence-record/1`、`edit-intent/1`、`write-receipt/1` 及三份交换文件相同 |
| 十条不变量 | 见 [02](02-architecture.md) §二 |
| 场景卡与方法卡 | 同一版本在四种 harness 中加载；版本写入任务记录 |
| 成本记录 | 同一口径，便于跨 harness 比较 |

## 七、上下文预算（建议值，阶段 1 实测后调整）

| 内容 | 预算 |
| --- | --- |
| 入口硬规则与工具组摘要 | 1,500–3,000 token，常驻 |
| 一个场景卡 | 6–10 KB，命中后加载 |
| 方法卡 | 每次命中部分不超过 2–3 张 |
| 工具定义 | 按需检索；常驻只保留工具组名称与一句说明 |
| 证据记录 | 每条只含字段与回放引用，不内嵌长描述 |

以现状估算（入口与路由约 2.2 万 token、一条口播链加载完约 5–6.7 万 token），阶段 1 的目标是把“开始工作前的常驻成本”降到现状的五分之一以下，并用 E3 检验路由准确率没有因此下降。
